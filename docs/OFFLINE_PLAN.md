# Offline / Read-Only PWA Plan

Goal: after a user logs in once and the app syncs data, `snobbin-web` should keep
working **read-only** while offline (no network), without forcing a re-login. Item
and group images should also render from cache while offline.

Two additional requirements drive the design:

- **Large groups.** Some groups have ~1,600 items. A single all-at-once snapshot is
  not viable. Sync must be **per-group, paginated, resumable, and progressive**.
- **Server-down tolerance.** The app must keep working when the API server itself is
  unreachable — not only when the device is offline. "Server down" looks *online* to
  the browser, so request failure must be treated as an offline trigger too.

Dominant real-world use is a **pure read**: "has this item been ranked yet?" That is
served entirely by the local mirror, which means we can ship read-only offline
**without** building a write/sync-back queue.

> **Status: experiment.** This is exploratory. If the spike (see §9) shows the
> approach is unworkable in the deployed environment, the changes are designed to be
> easily reverted (feature-flagged, additive modules, no server schema changes).

This document describes the current architecture, the constraints, and a phased
implementation plan.

---

## 1. Why this is non-trivial today

The app is built as a **server-first Next.js App Router** application:

- Every page is a React Server Component that reads Postgres via Drizzle:
  - `src/app/groups/page.tsx` → `getCurrentUserGroups()`
  - `src/app/groups/[groupId]/page.tsx` → `getGroupForCurrentUser()`, `getItems()`, `getGroupAttributeSummary()`
  - `src/app/activity/page.tsx` → `getPendingInvites()`, `getRecentItems()`
  - `src/app/layout.tsx` → `TopHeader` → `getCurrentUser()`
- `AuthInitializer` (`src/initializers/AuthInitializer.tsx`) calls `getSession()` on
  the server and **redirects to `/api/auth/login`** when there is no session.
  That is the "have to log in again" behavior.
- Data access is coupled to the session through `getCurrentUser()`
  (`src/server/utils/user/get-current-user.ts`), which throws if no session exists.
- Writes go through server actions (`src/server/actions/**`) and REST routes
  (`src/app/api/mobile/**`), both of which require a live DB + auth.
- Realtime updates use SSE (`src/hooks/useGroupEvents.ts` → `/api/groups/[groupId]/events`).
- Images are served by Cloudinary via `next-cloudinary`'s `CldImage`
  (`src/components/Image/ImagePreview.tsx`) — cross-origin, cache-busting URLs.
- The existing service worker is generated by `next-pwa` with default config
  (`next.config.mjs`) — it precaches the app shell only, not API data or images.

So "works offline" requires three independent pieces:

1. **Persisting the Auth0 session / user identity** so the app can render without a
   live session check (including when the API server is unreachable).
2. **A local data store (SQLite WASM) that shadows the server reads** so pages can be
   rendered from local data when the network or the server is unavailable.
3. **Caching images** (Cloudinary) in the service worker / Cache Storage.

## 2. Recommended technical approach

### 2.1 Local database: SQLite WASM in a Web Worker (OPFS)

Use **SQLite compiled to WASM** running in a dedicated Web Worker, persisted to the
**Origin Private File System (OPFS)**.

Recommended library: **[wa-sqlite](https://github.com/rhashimoto/wa-sqlite)**
(`rhashimoto/wa-sqlite`, MIT), using a **headers-free VFS**.

> **Spike finding (2026-10-19): SQLocal is ruled out.** SQLocal 0.18.0 wraps the
> official `@sqlite.org/sqlite-wasm` build and instantiates it with
> `sqlite3.oo1.OpfsDb` — the official `opfs` VFS, which requires `SharedArrayBuffer`
> and therefore **requires `COOP`/`COEP`** cross-origin isolation. It offers no
> `opfs-sahpool` option (verified in
> `node_modules/sqlocal/src/drivers/sqlite-opfs-driver.ts`). Since this app depends on
> cross-origin Auth0 login and Cloudinary, enabling COI is too risky for an
> experiment. **wa-sqlite's VFSes all state "No COOP/COEP requirements"**, so it is the
> chosen path.

**Chosen VFS: `OPFSCoopSyncVFS`** — OPFS-backed, runs in a worker, synchronous build
(fast), multiple connections allowed, filesystem transparent. Fallback:
`IDBBatchAtomicVFS` (IndexedDB-backed, works in all contexts, no headers) for browsers
where OPFS is unavailable.

wa-sqlite has **no first-party Drizzle driver**, so the local query layer goes through
`drizzle-orm/sqlite-proxy` with a small custom driver we write (route SQL → wa-sqlite
`sqlite3.exec`/prepared statements → rows). This is the main extra cost versus SQLocal,
and it is contained to one adapter file.

**Distribution note:** the npm package `wa-sqlite@1.0.0` is a **stale third-party
mirror** (single version, marked "Proprietary", missing modern VFSes such as
`OPFSCoopSyncVFS`). Consume wa-sqlite from the **GitHub repo `dist/`** (`.mjs` + `.wasm`)
instead — e.g. vendor the `dist/` + the needed `src/` files into `src/vendor/wa-sqlite/`,
or depend on the GitHub tag. Decide the exact mechanism in Phase 1.

#### Backend comparison (why we avoid the official build)

| Backend | Needs COOP/COEP? | Notes |
| --- | --- | --- |
| wa-sqlite `OPFSCoopSyncVFS` | **No** | **Chosen.** OPFS, worker, sync, multi-connection. |
| wa-sqlite `IDBBatchAtomicVFS` | **No** | Fallback. IndexedDB, all contexts. |
| wa-sqlite `AccessHandlePoolVFS` | **No** | OPFS, single connection only. |
| SQLocal (official `opfs` VFS) | **Yes** | **Ruled out** — see spike finding. |
| official `sqlite-wasm` `opfs` | Yes | Requires the headers; puts Cloudinary/Auth0 at risk. |
| `opfs-sahpool` (official) | No | Not exposed by SQLocal; only reachable via the official build directly. |

#### 2.1.1 What COOP/COEP actually are (plain-language)

SQLite WASM wants to read/write its database file synchronously from a worker, which
some builds implement using `SharedArrayBuffer`. Browsers only expose
`SharedArrayBuffer` to a page that is "cross-origin isolated," which you opt into by
sending two headers on every response:

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

Effectively: *"this page is a sealed room — nothing from other origins may load unless
it explicitly opts in."* That is why we prefer the backends above that don't need it.

For this app the headers put three things at risk:

- **Auth0 login** — the COOP docs explicitly warn cross-origin isolation "will break
  integrations that require cross-origin window interactions such as OAuth."
- **Cloudinary images/widgets** — `CldImage` transform URLs and the `CldUploadButton`
  widget must send CORP/CORS to load under `COEP: require-corp`.
- **Sentry Replay** (`replayIntegration` in `src/instrumentation-client.ts`) — loads
  cross-origin assets that COEP can block.

**Decision:** use wa-sqlite with a headers-free VFS. No `COOP`/`COEP` anywhere.

Alternatives considered:

| Option | Notes |
| --- | --- |
| `@sqlite.org/sqlite-wasm` (official) | Lowest-level; only `opfs-sahpool` avoids headers; you manage the worker/VFS/adapter yourself. |
| SQLocal | **Ruled out** — forces the header-requiring `opfs` VFS (spike finding above). |
| `sql.js` + `absurd-sql` | Older; IndexedDB-backed; higher overhead. |
| IndexedDB directly (Dexie) | No SQL; would require rewriting every query shape. |
| Replicache / PowerSync / TinyBase / cr-sqlite | Full sync engines — more than needed for read-only offline, and/or add cost/complexity. |

Because the requirement is **read-only offline**, we do not need a full bidirectional
sync engine. We only need a one-way **server → local mirror** plus a local query layer.
This keeps the change small and reversible.

### 2.2 Schema mirror

Define a **client-side schema** that mirrors the read models the pages need. We do not
need every server table; only what the read pages render:

- `groups`
- `group_members` (+ member `snobs`)
- `group_attributes`
- `group_invites`
- `items`
- `item_attributes`
- `rankings`
- `recent_items` (activity)
- `pending_invites` (activity)
- `current_user`
- `sync_meta` — per-group sync state, e.g.
  `group_id`, `last_synced_at`, `complete` (bool), `highest_page_synced`,
  plus global `schema_version` / `last_full_sync_at`.

These map closely to `src/server/db/schema.ts` and to the JSON shapes produced by
`src/server/utils/mobile/mobile-formatters.ts` (already snake_case and stable).

### 2.3 Sync: per-group, paginated, resumable, progressive

A single snapshot endpoint is **not viable** — groups can contain ~1,600 items and the
app must tolerate a slow or failing server. Instead:

**Sync order (cheap → expensive):**

1. **Bootstrap (tiny, always first):** current user profile + the list of groups the
   user belongs to + memberships. This is one small request and is enough to render
   `/groups`, the header, and offline detection.
2. **Per-group items, paged:** fetch items for a group using the **same pagination the
   UI already uses** (`pageSize = 20`, plus keyword/sort/status/attribute filters as
   in `src/server/utils/items/get-items.ts`). Write each page into SQLite.
3. **Per-group supporting data:** attributes, item attributes, rankings, members,
   invites (per group).
4. **Activity data:** recent items + pending invites (small).

**How a large group gets fully mirrored:**

- **Progressive / lazy fill (default):** while online, every page the user actually
  views is written to SQLite. Over normal use a big group fills in on its own. This is
  the zero-effort path and matches the dominant "check if ranked" usage.
- **Explicit "Sync group for offline" (opt-in):** an action that pages through the
  whole group in the background with a progress indicator, for groups the user really
  wants fully available offline.
- **Resumability:** `sync_meta.highest_page_synced` + `complete` let a sync resume
  after interruption instead of restarting.
- **Incremental refresh:** after the first full mirror, re-fetch only what changed,
  filtered by `updated_date` (items) and the corresponding timestamps for rankings, so
  repeat syncs are cheap.

**Endpoint shape (recommended):** dedicated, paginated offline routes, reusing the
existing `mobile-formatters` shapes:

```
GET /api/offline/bootstrap                      # identity + groups + memberships
GET /api/offline/groups/:groupId/items?page=N   # paginated items (pageSize 20)
GET /api/offline/groups/:groupId/meta           # attributes, members, invites
GET /api/offline/groups/:groupId/rankings?page=N
GET /api/offline/activity                       # recent items + pending invites
GET /api/offline/changes?since=<timestamp>      # incremental refresh (optional, later)
```

The existing `GET /api/mobile/user/:userId/groups` and
`GET /api/mobile/groups/:groupId` remain as an alternative source; they already return
complete per-group datasets. For small groups they are fine as-is; for large groups use
the paginated offline routes above. All are auth-guarded (`requireAuth` /
`requireMember`), so once we can mint a token from the web session they are a clean,
versioned sync contract.

**Transactionality:** write each page in its own SQLite transaction (never one giant
transaction for a whole group). Upsert by id so refresh is idempotent.

### 2.4 Keeping the session so the user is not logged out

The Auth0 session cookie is what triggers the redirect in `AuthInitializer`. Two
changes are needed:

1. **Cache the identity locally.** Persist the minimal `Snob` profile (id, email,
   name, pictureUrl, lastGroupId, isPremium) and the `sub` in the local store (and/or
   a `localStorage` key) at sync time. Offline rendering uses this instead of calling
   `getCurrentUser()`.

2. **Make the shell render without a live session — including when the server is
   down.** Restructure so that:
   - The server components that require a session are **not** the thing that blocks
     first paint when offline.
   - The app renders a client-side offline shell that reads from the local store when
     the server is unavailable, and only calls the server path when it is reachable.

Concretely:
   - Move the "is the user logged in" decision out of the RSC `redirect` path for the
     offline case. `AuthInitializer` should still use `getSession()` when the server is
     reachable, but when it is not it must **not** redirect to `/api/auth/login`.
   - Introduce a small client `ConnectivityProvider` that tracks connectivity and
     local-data availability (see §2.4.1).

#### 2.4.1 "Offline" means "server unreachable", not just `navigator.onLine`

The browser reports `navigator.onLine === true` even when the API server is down or
returning 5xx. Therefore the offline trigger must be **any of**:

- `navigator.onLine === false`, **or**
- a bootstrap/sync request failed (network error, timeout, or 5xx), **or**
- the session check itself threw.

We treat all three as "use local data + cached identity". The app then retries
bootstrap in the background and flips back to the server path when it succeeds. A
small exponential-backoff retry plus an `online` event listener covers recovery.

Note on token lifetime: Auth0 refresh tokens are the durable credential; the ID/access
tokens expire. For **read-only** offline we do not call any auth-guarded endpoint, so
we only need the cached identity + local mirror — the session cookie/refresh token is
only exercised when the user comes back online. When back online, if the refresh token
is valid, Auth0 transparently re-establishes the session (no re-login prompt); if it is
revoked/expired, the user is asked to log in again, which is acceptable.

### 2.5 Rendering path when offline

The core change: **every read page needs an offline-aware data source.**

Introduce a repository boundary, e.g. `src/data/`:

```
src/data/
  server/        # existing server-only reads (current code, unchanged signatures)
  local/         # SQLite-backed reads with identical return types
  repository.ts  # picks local vs server based on connectivity / availability
```

Each page currently calls server util functions directly. We refactor those reads
behind a shared interface so the same component tree can be fed from either source.
The cleanest incremental pattern is:

1. Keep the RSC pages for the **online** path (server render, fast, SEO/SSR).
2. Add a **client-side offline fallback**: when a page cannot be server-rendered
   (navigation fails, or the server is unreachable after hydration), render the same
   presentational components from local data.

Because the presentational components (`GroupDetails`, `ItemList`, `ItemCard`, etc.)
are already `"use client"` and take plain props, they can be reused unchanged as long
as the local repository returns the same shapes (`SnobGroup`, `PaginatedResults`,
`SnobGroupAttributeSummary[]`, `SnobGroupInvite[]`, `RecentRankingItem[]`).

### 2.6 Pagination, search, sort, and filters offline

`getItems()` in `src/server/utils/items/get-items.ts` supports pagination, keyword
search (ILIKE), sort, and attribute filters. The local SQLite implementation must
replicate these queries (SQLite supports `LIKE`, `ORDER BY`, `LIMIT/OFFSET`, and
`EXISTS`) using the mirrored tables. This is a near 1:1 translation.

Note: SQLite's `LIKE` is case-insensitive for ASCII by default, which matches the
intent of `ILIKE` for the common case.

### 2.7 Realtime offline

SSE (`useGroupEvents`) will fail offline. `EventSource.onerror` is already tolerated,
so no crash — but we should:
- Skip opening the `EventSource` when offline.
- Re-open it on `online` and trigger a resync.

## 3. Image caching

Two classes of images are loaded by the app:

1. **Cloudinary item/group images** via `CldImage`
   (`src/components/Image/ImagePreview.tsx`, `GroupAvatar`, `ProfileAvatar`).
   `CldImage` generates optimized Cloudinary URLs (often cross-origin, with transform
   segments). These are the large, important ones to cache.
2. **Local static assets** (icons, logo) — already precached by `next-pwa`.

Plan:

- **Service worker runtime caching** for Cloudinary image responses, using a
  stale-while-revalidate or cache-first strategy with a bounded entry count and
  expiry. `next-pwa` wraps Workbox, so add `runtimeCaching` rules in
  `next.config.mjs` for `res.cloudinary.com` (and any custom Cloudinary domain),
  matching `image`/`fetch` destinations.
- **Eager warm-up**: after a successful sync, walk the items/group/profile
  `imageUrl`/`pictureUrl` values and `fetch()` them once (through the SW) so they are
  present in Cache Storage before the user goes offline. Cap the number/size and
  prefer thumbnail-sized Cloudinary transforms so the cache stays reasonable.
- **Offline rendering**: `CldImage` currently requests a transformed URL. Ensure the
  cached URL exactly matches the URL used at render (same transform params), otherwise
  the cache misses. Simplest robust approach: request a canonical thumbnail transform
  (e.g. `w_200,h_200,c_fill`) for the list view and cache that exact URL; the enlarged
  modal image can fall back to the cached thumbnail or show a placeholder offline.
- **Quota handling**: OPFS/SQLite and Cache Storage share the origin storage quota.
  Call `navigator.storage.persist()` after first successful sync to reduce eviction
  risk, and expose a "storage used" indicator + clear-cache action in the profile page.

## 4. Phased implementation plan

### Phase 0 — Foundations & decisions (SPIKE FIRST)
- Spike **done for the library/header question**: SQLocal ruled out (needs COOP/COEP);
  **wa-sqlite + `OPFSCoopSyncVFS`** chosen (headers-free). See §2.1 / §9.
- Add feature flag `NEXT_PUBLIC_OFFLINE_ENABLED` (build-time env var) to gate the
  offline code path so it can be disabled instantly.

### Phase 1 — wa-sqlite plumbing + local schema
- Vendor wa-sqlite from GitHub `dist/` (`.mjs` + `.wasm`) and the needed `src/` files
  (VFS classes) — do **not** use the stale npm mirror.
- Stand up the worker + `OPFSCoopSyncVFS`; verify OPFS persistence with
  `crossOriginIsolated === false` (spike re-check).
- Write the Drizzle `sqlite-proxy` driver adapter over wa-sqlite
  (`src/data/local/sqlite-proxy-driver.ts`).
- Define `src/data/local/schema.ts` (client-side SQLite Drizzle schema mirroring the
  read models).
- Add a browser-side migration runner (Drizzle's Node `migrate()` is not usable in the
  browser; run generated SQL through the worker).
- Add `sync_meta` per-group state handling (`last_synced_at`, `complete`,
  `highest_page_synced`) and a `localDataAvailable()` capability check.

### Phase 2 — Paginated, resumable sync
- Add the paginated offline endpoints (§2.3): `/api/offline/bootstrap`,
  `/groups/:groupId/items?page=N`, `/groups/:groupId/meta`, `/groups/:groupId/rankings`,
  `/api/offline/activity`. Reuse the `mobile-formatters` helpers and the same
  `pageSize`/filter semantics as `getItems()`.
- Add the client sync engine:
  - `syncBootstrap()` — identity + groups + memberships (small, always first).
  - `syncGroupPage(groupId, page)` — one page per SQLite transaction, upsert by id.
  - `syncGroupFully(groupId)` — background pager for the explicit "sync for offline"
    action, with progress + resumability via `highest_page_synced`.
  - `syncActivity()`.
- **Progressive fill:** hook the online page renders so any page the user views is
  written to the mirror automatically (no explicit action needed).
- Trigger sync: after login/first online load, on `online` (with backoff on failure),
  optionally on an interval, and after successful writes.
- Persist cached identity (`Snob` + `sub`) alongside the mirror.
- Warm the image cache for whatever was synced; call `navigator.storage.persist()`.

### Phase 3 — Connectivity / session shell
- Add `ConnectivityProvider` exposing `isOnline` (network **and** server reachability),
  `hasLocalData`, `lastSyncedAt`, plus a backoff retry against `/api/offline/bootstrap`.
- Treat **request failure / 5xx / session-check error** as offline, not just
  `navigator.onLine === false` (see §2.4.1).
- Rework `AuthInitializer` so a user with a cached identity is **not** redirected to
  login when the server is unreachable:
  - Server: keep `getSession()` for the reachable path.
  - Offline/down path: render the shell from the cached identity.
- Show a subtle persistent offline indicator in the header (icon + popover with
  "read-only, changes disabled"), rather than a full-width banner.
- Disable/hide all mutation entry points while offline (see Phase 6).

## 5. Data flow summary

```
Online, first load
  login (Auth0) ─▶ session ─▶ RSC pages (server reads from Postgres)
                          └─▶ syncBootstrap()  ─▶ GET /api/offline/bootstrap
                                                ─▶ SQLite (OPFS) mirror + cached identity
                          └─▶ progressive fill ─▶ GET /api/offline/groups/:id/items?page=N
                                                ─▶ upsert page into SQLite (per page txn)
                          └─▶ warm Cloudinary image cache (+ storage.persist())

Offline OR server unreachable
  ConnectivityProvider.isOnline === false   (network down, 5xx, timeout, or fetch throw)
    └─▶ no redirect to login (cached identity exists)
    └─▶ pages render via src/data/local repositories (SQLite reads)
    └─▶ "has this item been ranked?" answered purely from the mirror
    └─▶ images served from Cache Storage via service worker
    └─▶ write controls disabled (read-only)
    └─▶ background retry with backoff

Recovered
  bootstrap succeeds ─▶ refresh open group ─▶ router.refresh() ─▶ SSE reconnects
  (failed bootstrap is treated as offline, not as a logout)
```

## 6. Constraints, risks, and open questions

- **Cross-origin isolation (COOP/COEP).** Avoided entirely by choosing wa-sqlite with a
  headers-free VFS. The header-requiring route (`opfs`) would put Cloudinary images,
  Auth0 redirects, and Sentry at risk, and is why SQLocal was rejected. Re-confirm in
  the remaining spike items that no header is needed in the deployed environment.
- **Auth0 session vs. server-down.** `getSession()` is server-side; when the server is
  down there is no server. The cached client identity is the source of truth **only**
  for the read-only offline path, never for writes.
- **Bundle/runtime cost.** SQLite WASM adds a worker bundle + WASM asset. Load lazily
  only when needed (after first sync / on first offline or group open).
- **Storage quota & eviction.** OPFS and Cache Storage share a quota; a 1,600-item
  group plus images can be large. Cap cache sizes, sync large groups on demand rather
  than eagerly, request persisted storage, and surface usage to the user.
- **Multi-tab / multi-user.** A single shared SQLite file is not concurrency-safe
  across tabs without coordination. Read-only usage is mostly fine, but consider a
  Web Locks / BroadcastChannel guard and per-`sub` database naming.
- **Cache-busting image URLs.** Cloudinary transforms produce different URLs per size;
  the offline cache must key on the exact rendered URL. Decide a canonical transform.
- **Schema drift.** Local mirror must be versioned; on `schemaVersion` mismatch, wipe
  and re-sync (safe because offline is read-only).
- **Partial group data.** A group may be only partially mirrored. The UI must not imply
  completeness offline — show "last synced" and mark groups that are partial.
- **`next-pwa` vs. Serwist.** `next-pwa` is no longer actively maintained; if SW work
  grows, consider migrating to Serwist. Not required for the initial cut.

**Service worker install fix (found during production validation, 2026-10-19)**

The generated service worker went straight to `redundant` — offline was completely
disabled. Root cause: `next-pwa`'s precache manifest listed entries that do not return
200 in production, and **one** non-200 entry fails the whole Workbox install:

- 46 × `.js.map` — listed by `next-pwa` but never emitted to `.next/static`.
- 1 × `/_next/app-build-manifest.json` — served via the app router, so the auth guard
  redirects it (307 → `/api/auth/login`).

Fix: `buildExcludes: [/\.map$/, /app-build-manifest\.json$/]` in `next.config.mjs`.
After rebuilding, all **69** precache entries return 200 and the worker activates
(`active: "activated"`, `controller: true`, 70 cache entries).

> Note: this was a **pre-existing** misconfiguration that only surfaced once an offline
> feature existed to depend on the service worker. It affects the current production app
> too — the PWA has never had a working service worker.


**Offline read-path fixes (2026-10-20)**

Beyond the spike, making the *actual* app work offline required four fixes to
shared code, all found during production validation:

1. **`AuthInitializer` must not force a re-login when the session check *fails*.**
   Previously `LoginCheck` called `getSession()` and redirected to
   `/api/auth/login` on any falsy result — and threw if the backend errored
   (DB/API down). Now, when `OFFLINE_ENABLED`, a **thrown** session check (or a
   failed `checkForNewUser` write) lets the shell render instead of bouncing to
   login. A genuinely absent session still redirects, preserving normal behaviour.
   This is the plan's §2.4.1 trigger "the session check itself threw".

2. **Offline query changes must not use the router.** Pagination, sort, filter
   and search went through `router.push`, which performs an RSC fetch that cannot
   be served offline. `GroupPageClient` now owns the query params in local state
   when reading from the mirror and injects an `onUpdateQuery` override down
   through `GroupDetails` → `ItemList`; the mirror is re-read locally instead.
   When the server comes back the override is dropped.

3. **The service worker must actually register** (see the install-fix note above):
   `next-pwa`'s auto-register targets the Pages Router `main.js` entry, which the
   App Router never loads. Registration is now done explicitly in
   `src/initializers/PwaInitializer.tsx` (`register: false` in `next.config.mjs`).

4. **A full page reload must be served from cache** (found during user testing,
   2026-10-20). `next-pwa`'s default cache config contains exactly one navigation
   rule — a `NetworkFirst` hardcoded to the exact path `/` — and registers **no**
   `NavigationRoute` or navigation fallback. A hard reload of a deep URL such as
   `/groups/<id>` is therefore a *navigation* request that matches only the generic
   `others` rule (`NetworkFirst`, `networkTimeoutSeconds: 10`, `maxEntries: 32`).
   Client-side navigation worked, but a full reload failed: a navigation request
   that is not the homepage had no reliable cached-document handler.
   Fix: register an explicit `documents` route **first** in `runtimeCaching`
   (`request.mode === "navigate"`, `NetworkFirst`, 3 s timeout, 200 entries) so every
   navigation falls back to its cached document as soon as the network fails.
   Order matters — Workbox uses the first matching route, and `runtimeCaching` order
   is registration order.

   > This is also **pre-existing**: before this fix, the deployed app could not
   > survive a hard reload of any non-home route while offline.

5. **A 5xx response must be treated as "server unreachable"** (found 2026-10-22).
   Workbox's stock `NetworkFirst` returns *any* resolved response — including a
   `502/503`. When the app runs behind a reverse proxy (Coolify/nginx) a crashed
   backend usually returns **502**, so a reload would show the proxy's error page
   instead of the cached app (verified: `browser.navigate` → `502 Bad Gateway`).
   This directly violated "keep working when the API server is down".

   Fix: switch `next-pwa` to **InjectManifest** (`swSrc: "sw.js"`) and implement the
   navigation handler ourselves: on network error, timeout (3 s), **or `!response.ok`**
   it serves the cached document. The handler also refuses to cache cross-origin
   responses (e.g. the Auth0 login page reached through a redirect). All previous
   `runtimeCaching` rules moved into `sw.js`, so route order is explicit in one file.

   Verified: with the server **stopped** (the harness proxy returns 502), `/groups`,
   `/activity`, `/profile` and `/` all load from cache; `/` redirects to the last
   group and renders its 1,624 items from the mirror.

**Remaining read paths (2026-10-22)**

`/groups`, `/activity`, `/profile` and `/` now fall back to the mirror too (see
Phase 4). Supporting local reads: `getLocalGroups` (membership + soft-delete
filtered), `getLocalCurrentUser`, `getLocalLastGroupId`, `getLocalPendingInvites`,
`getLocalRecentItems`. `applyBootstrap` now records the *database* snob id in
`localStorage` (separate from the Auth0 `sub`) so "me" can be resolved offline.

**Production hardening (2026-10-22)**

Moving from the validated spike to a shippable read-only experience:

1. **Background auto-sync on group load** (`src/hooks/useAutoSync.ts`, called from
   `GroupPageClient`). Visiting a group online silently mirrors it; there is no
   "sync for offline" button any more. Properties: non-blocking, per-group deduped,
   resumable (`highestPageSynced`), aborted on unmount, and gated on a known
   identity so it never writes to the anonymous database.
2. **Staleness TTL.** A fully-mirrored group is considered fresh for 24 h. After
   that it re-mirrors from page 1 in the background. This matters because resuming
   a *complete* group would start past the last page and refresh nothing.
3. **`navigator.storage.persist()`** is requested before syncing so the mirror is
   not treated as best-effort storage (Safari evicts site data after ~7 days of
   non-use; pressure eviction would silently disable offline reading).
4. **Per-user mirror isolation + logout wipe.** The SQLite file name is derived
   from the Auth0 `sub` (`offlineDbNameFor`), kept in `localStorage` so it is
   readable with no network. A different account opens a *different* database and
   the previous user's rows are wiped on identity change (`OfflineIdentitySync`).
   Logout clears the mirror and the Cloudinary/next-image runtime caches before
   redirecting (`useOfflineLogout`). Previously a single shared database meant a
   second user on the same device could read the first user's cached groups.
5. **API routes are no longer flag-gated.** `/api/offline/*` must stay reachable
   because background fill runs in the normal deployed app. The flag now gates the
   offline read-only *UI* only.
6. **Removed** the `/offline-spike` debug page (it was publicly reachable) and the
   `SyncGroupButton` component.
